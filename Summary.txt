2. WHAT WORKED
================================================================================

[W1] AITER FMHA prefill crash — FIXED, root-caused
  Symptom: server died in compile_or_warm_up_model, before binding:
    TypeError: fmha_fwd_bf16_opus_fwd(): incompatible function arguments
  Cause: aiter/jit/utils/cpp_extension.py:1664 injected standalone pybind11
    3.1.0 (PYBIND11_INTERNALS_VERSION 12) via -I, outranking the -isystem path
    with torch's bundled pybind11 3.0 (version 11). The 117 prebuilt aiter .so
    files use v11. pybind11 keeps a SEPARATE type registry per internals id, so
    the JIT module could not see aiter_tensor_t from the v11 core.
  Proof after fix: rebuilt module reports __pybind11_internals_v11 and its
    signature resolves to aiter.jit.module_aiter_core.aiter_tensor_t (was a
    bare, unqualified aiter_tensor_t from its own registry).
  Deliverables: /home/asirra/aiter-pybind11-internals.patch
                /home/asirra/apply_aiter_pybind11_fix.sh (idempotent)
  MEASURED cold prefill (single request, no cache):
    context ~24k : FLASH_ATTN 12,953 -> AITER 13,524 tok/s   (+4.4%)
    context ~93k : FLASH_ATTN 11,174 -> AITER 13,423 tok/s   (+20.1%)
  IMPACT ON E2E: small. Prefill is 5.8% of wall clock, so +20% prefill is
    ~1% E2E. Worth shipping, NOT the lever that closes the gap.

[W2] MLA prefill backend pin — unblocked CI
  --attention-config '{"mla_prefill_backend":"FLASH_ATTN"}' let the server boot
  while AITER FMHA was broken, keeping ALL AITER MoE kernels.
  Throughput with pin: 17.0-17.8 tok/s generation vs ~3 tok/s on the
  EMULATION MXFP4 path. Verified in CI job 94402537049 (server reached
  "Application startup complete", engine init 188.75 s, no AITER crash).

[W3] EVAL_ONLY unbound variable — FIXED
  kimik3_fp4_mi355x_mtp.sh used bare "${EVAL_ONLY}" under `set -u` while
  launch_mi355x-amds.sh never exports it. Killed a 40-minute run AFTER the
  server was already healthy:
    line 243: EVAL_ONLY: unbound variable
  Fix: "${EVAL_ONLY:-false}". Confirmed by the next run getting past it.

[W4] AITER MoE kernels confirmed active
  With the full env block: flydsl_moe1_afp8_wfp4_bf16_* / "FlyDSL MoE".
  Without VLLM_ROCM_USE_AITER_MOE_SITUV2_A8W4=1 you fall back to
  "Using 'EMULATION' Mxfp4 MoE backend" at ~3 tok/s. Keep all exports.

[W5] Prefix caching works — earlier "0 hits" was OUR misconfiguration
  Missing PYTHONHASHSEED=42 (needed for identical block keys across the 8
  ranks under SimpleCPUOffloadConnector). With it set: 15,360 hits /
  145,919 queries. A repeated 24k prompt went 12.11 s -> 0.90 s on cache hit.
  NOT a vLLM bug. Retracted.

3. WHAT DID NOT WORK
================================================================================

[F1] Commenting out the AITER export block — WRONG FIX
  Leaves VLLM_ROCM_USE_AITER=1 (the sole crash trigger, since
  AiterFlashAttnPrefillBackend.is_available() consults only
  rocm_aiter_ops.is_enabled()) while discarding the MoE kernels and
  VLLM_USE_BREAKABLE_CUDAGRAPH=0. Same crash, worse performance.
  Also: VLLM_ROCM_USE_AITER_MHA=0 does NOT disable the AITER prefill path.

[F2] rejection_sample_method "synthetic" — CORRUPTS OUTPUT
  Commits draft tokens WITHOUT verifying against the target.
  On the EMULATION path: ~1500 tokens of "-2-3-2-2-" garbage.
  On the AITER path: fluent but wrong — dropped/incorrect words, e.g.
    "designed to tasks that typically require intelligence"
    "b displacement" / "a tool with patterns from patterns"
  Reported acceptance merely echoes the hardcoded constant (mean 2.46-2.53 vs
  configured 2.51; per-position acceptance pinned at exactly 1.000).
  With "standard" or "block": clean text, finish_reason stop.
  The repo already uses "block" when EVAL_ONLY=true. The agentic replay
  depends on parseable tool calls, so this arm is running on invalid output.

[F3] conc16 + ep8 — MAJOR REGRESSION
  28.2% success vs 73.5%; output 56.2 vs 104.6 tok/s; TTFT 19.45 vs 3.33 s;
  crashed after 498 s instead of 2,219 s.
  Confound: this run changed TWO variables (conc 10->16 AND ep 1->8), so the
  regression cannot be attributed to either alone.

[F4] KV block-pool corruption — UNFIXED, THE REAL BOTTLENECK
  Two distinct asserts, same underlying area (prefix cache + CPU offload):
    conc10: kv_cache_utils.py:292  assert curr_block is not None
            (free-list shorter than num_free_blocks claims — counter desync)
    conc16: block_pool.py:667      assert block.ref_cnt == 0
            (block on the FREE list still referenced — refcount corruption)
  Both reached via allocate_slots -> ...allocate_*_blocks -> get_new_blocks.
  Effect: engine dies mid-run, 26.5%-71.8% of requests fail, and surviving
  requests emit only 24-32% of expected tokens.
  This costs more throughput than every kernel optimisation combined.

[F5] FP8 prefill query quantization — NOT AVAILABLE ON ROCm
  B300 uses --attention-config '{"use_prefill_query_quantization":true}'.
  backend_supports_prefill_query_quantization() requires device capability
  100 (GB200/Blackwell) and only FlashInfer / TRT-LLM Ragged backends.
  Structurally unreachable on MI355X. Part of B300's prefill lead is not
  closable by configuration.

      ValueError: Selected backend ROCM_AITER_MLA is not valid for this
      configuration. Reason: ['non-causal attention not supported']
    The DSpark draft is non-causal; TRITON_MLA is the ONLY ROCm MLA backend
    with supports_non_causal_multi_token_decode = True. So the backend cannot
    be swapped by configuration on ROCm.

  THE HIDDEN COST (found by review, not in any log):
    v1/worker/gpu/spec_decode/dflash/speculator.py:110-127 -- once the target
    is downgraded to PIECEWISE, wants_full is False and the DSpark drafter is
    given CUDAGraphMode.NONE, i.e. FULLY EAGER. No warning is emitted. Every
    draft layer, the Markov head and the per-step sampling loop dispatch
    kernel-by-kernel from Python on every decode step.

  IN-CONTAINER SOURCE PATCH (validated):
    vllm/v1/attention/backends/mla/triton_mla.py
      _cudagraph_support: UNIFORM_SINGLE_TOKEN_DECODE -> UNIFORM_BATCH
    Justified by the file's own existing comment, which raises the reorder
    threshold "so full-cudagraph capture admits it", and by
    supports_non_causal_multi_token_decode = True already being set.

  MEASURED (single stream, 600-token generations, block sampling, AITER prefill):
    downgrade warning : GONE
    graph capture     : succeeded in 42 s
    correctness       : "17*23" -> 391, finish_reason stop  (output valid)
    decode            : 76.2 / 78.2 / 78.5 tok/s
    ITL               : 13.12 / 12.78 / 12.74 ms
  For reference the CI conc10 run measured ITL 90.4 ms (at concurrency 10, so
  not a like-for-like comparison). A same-config unpatched baseline is being

[P2] KV offload DRAM budget
  B300: 236,125,000,000 B/rank (~1,889 GB). Ours: 187,375,000,000 (1,499 GB),
  from dram-utilization 0.50. Host has 3,023 GB. More offload capacity should
  raise prefix-cache hit rate on agentic traces with large shared prefixes.

[P3] cudagraph_capture_sizes shape alignment
  Ours: 1..60 (mode 3, FULL_AND_PIECEWISE, custom_ops).
  B300: [3,6,...,48] only — multiples of (1 + num_speculative_tokens).
  Ours covers those values, but the elaborate config may be buying nothing
  once FULL is downgraded to PIECEWISE anyway.

[P4] max_num_seqs 20 (ours) vs 16 (B300).

6. THROUGHPUT MODEL (from review) — CORRECTS EARLIER CLAIMS
================================================================================
  output_tok/s = C x U / ITL   (C = concurrency, U = decode duty cycle)

                    C     ITL       ideal C/ITL   measured   U
    ours  c10      10    0.0904        110.6       104.6     0.946
    ours  c16      16    0.1092        146.5        56.2     0.384
    B300  c8        8    0.0042       1904.8       293.4     0.154
    B300  c16      16    0.0077       2077.9       347.9     0.167

  Run A is already at 94.6% of what its own per-token speed permits.
  => Fixing the KV block-pool crash is worth only ~5.7% of throughput DIRECTLY.
     I previously called it the dominant lever. That was WRONG. Its real value
     is as the GATE on running higher concurrency.
  => AITER prefill is worth ~0.97% of E2E (prefill is 5.8% of wall clock).
     Also previously overstated.
  => The entire 2.8x gap is per-token speed. 227 ms/step is ~20x more than
     HBM bandwidth can explain, so we are launch/CPU-bound, not memory-bound.
     That is exactly the signature of an eager drafter.

  Measured concurrency scaling from our own two points: throughput ~ C^0.598.
